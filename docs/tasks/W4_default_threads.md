# W-4: 既定スレッド数抑制の解除

## 1. 目的

`ensure_sane_thread_count()` (src/sparse.cpp) は OMP_NUM_THREADS 未設定時に
既定 1 スレッドへ強制抑制している。これは P2-1 開発時に観測された、オーバー
サブスクライブ/仮想化されたサンドボックでの OpenMP スレッドチーム起動レイテンシ
がワークロード本体を圧倒する「見かけ上のハング」への対策として導入された
(src/sparse.cpp のコメント、コミット履歴参照)。実マルチコア環境ではこの
抑制が既定性能を不必要に殺している。本タスクは、明示的な上書き手段を追加し、
既定値を「安全側だがより並列」なものへ変更する。

## 2. 現状分析

- `ensure_sane_thread_count()`: OMP_NUM_THREADS 未設定 かつ
  `omp_get_max_threads() > 1` のとき `omp_set_num_threads(1)` を実行。
  `cg()`/`bicgstab()` など線形ソルバ呼び出しの都度、遅延初期化される
  `static const bool kDone` 経由で一度だけ実行される(static initializer
  順序未定義の起動時ハングを避けるため、意図的に関数ローカル static)。
- `run_ted` (src/diffusion.cpp:1516-1521) の `OmpThreadGuard(1)`: TED
  反応パスの時間ループ全体を強制シングルスレッド化する別の仕組み。
  コメント (1505-1515行) によれば、これは前者と**同一の原因ではない**:
  問題サイズが数千未知数程度と小さく、Picard/CG の反復回数が多いケースで、
  多数の小さな OpenMP 並列領域それぞれのスレッドチーム起動オーバーヘッドが
  累積し、定数倍のスローダウンになる、という**この環境固有ではない一般的な
  小問題オーバーヘッド**の対策。「変更前後で結果は不変、wall time のみ変化」
  と明記されている。

## 3. 実装方針

### 3.1 明示的上書き: `CPROCESS_THREADS` 環境変数

ParamDB キーではなく環境変数 `CPROCESS_THREADS` を選択した。理由:
- `ensure_sane_thread_count()` は `ParamDB` にアクセスできない/依存させたくない
  低レベルユーティリティ (sparse.cpp はソルバプリミティブの並進 TU で、
  ParamDB は上位層の proc:: 設定機構)。既存の `OMP_NUM_THREADS` 判定と
  同じ「環境変数を起動時に一度読む」構造にそのまま合流させる方が
  既存コードとの一貫性が高く、余分な依存関係を増やさない。
- 優先順位: `CPROCESS_THREADS` (設定時、正の整数なら最優先) →
  `OMP_NUM_THREADS` (設定時は OpenMP ランタイム既定に任せ、何もしない、
  従来通り) → どちらも未設定なら新既定値 `min(hardware_concurrency(), 8)`。

### 3.2 既定値変更 — 実測により変更、既定は 1 のまま維持

当初 `min(std::thread::hardware_concurrency(), 8)` を既定値として実装し、
決定性テストを実行したところ、`test_species_parallel`
(`species_parallel=-1` と `=1` の等価性を相対誤差 <1e-12 で assert)が
**スレッド数 2/4/8 のいずれでも FAIL** した(実測: 1 スレッドで
`maxrel=0`、2 スレッドで `maxrel=1.05e-12`、4 スレッドで
`maxrel=1.14e-12`、既定 4 コア環境で `maxrel=1.68e-12`)。原因は、
比較対象の 2 経路(逐次種ループ vs 並列種ループ)がそれぞれ内部で
CG/BiCGStab の OpenMP reduction(`dotv`/`axpy`)を使っており、
スレッド数が 1 を超えると加算順序が経路ごとに異なる形で変わり、
「同一の演算を同一順序で行うので bit 一致する」という
`test_species_parallel.cpp` 自身のコメント上の前提
(「per-species subproblems are fully independent so the parallel path
uses the exact same math」)が崩れるため。この前提はテストコード自身が
明記しているとおり「経路が同一演算列を辿る」ことに依存しており、それは
スレッド数 1(=OpenMP 並列領域が宣言順に逐次実行される)でしか保証されない。

この実測結果を踏まえ、**既定値は変更せず 1 のまま維持する**方針に変更した
(3.5 節に測定根拠を記載)。既定を上げると、この決定性テストに限らず
スイート内の他の「経路 A vs 経路 B の bit 一致/近接一致」を assert する
テスト群でも同種の破綻が潜在的に起こりうり、W-4 の目的(性能改善)より
CLAUDE.md/タスク要求(既存決定性テストの PASS 維持)を優先すべきと判断した。

`CPROCESS_THREADS=N` による明示的なオプトインのみを提供する:
呼び出し側が「このワークロードは経路間 bit 一致に依存しない」と判断できる
場合にのみ、環境変数で複数スレッドを要求できる。オーバーサブスクライブ
検知(軽量ベンチマークで並列領域起動を計測し、異常に遅ければ 1 に
フォールバックする方式)は当初から既定値変更とセットで検討していたが、
既定値自体を変更しない結論になったため同様に見送り(3.3 参照)。

### 3.3 オーバーサブスクライブ検知の見送り

計測ベンチマークをその場で実行し閾値判定するアプローチは、閾値の較正に
実ハードウェアでの反復計測が必要であり、本タスクの実行環境
(コンテナ、`nproc`=4 だが仮想化特性不明)ではその較正ができない。
誤ったヒューリスティックは「常に安全側 1 に倒れて意味がない」出力か、
逆に「検知が効かずハングを再現する」出力のどちらかになりうる。
明示的環境変数 + 保守的既定値の組み合わせのほうが、この環境で検証
可能な範囲で安全である。将来 実マルチコア/複数世代のハードウェアで
計測できる環境が用意でき次第、`CPROCESS_THREADS` 未設定時のみ動作する
起動時ベンチとして追加することを推奨する。

### 3.4 `run_ted` の `OmpThreadGuard(1)`

**現状維持**(縮小しない)。理由:
- コメント (diffusion.cpp:1505-1515) が示す原因は「小さな並列領域の
  起動オーバーヘッド累積」であり、特定の 1 個の問題ループではなく
  反応パス全体で繰り返し呼ばれる CG/BiCGStab 呼び出し全体に及ぶ。
  ガード対象を一部ループへ絞ると、絞り漏れた呼び出しで同じ問題が
  再発する可能性が高く、絞り込みの正しさを検証する決定的な方法
  (問題サイズ・反復回数がケースごとに変わる)がこの環境では確立できない。
- CLAUDE.md の指示どおり「確信を持って縮小できない場合は現状維持し
  理由を記録する」を採用した。
- なお `OmpThreadGuard(1)` は `ensure_sane_thread_count()` の新既定値
  (>1 スレッド)より**後で**評価される(`run_ted` 内で
  `omp_set_num_threads(1)` を明示上書きするため)。よって W-4 の既定値
  変更は `run_ted` の外側で呼ばれる線形ソルバ(通常の `diffuse`/`react`
  パス、`cg_amg` 等のテスト経路)には効くが、TED 反応パス自体は
  引き続き 1 スレッドで動く。これは意図した挙動であり、3.4 の理由により
  今回は変更しない。

## 4. 変更箇所

- `src/sparse.cpp`: `ensure_sane_thread_count()` に `CPROCESS_THREADS`
  (正の整数なら最優先で `omp_set_num_threads`)を追加。既定ロジック自体
  (`OMP_NUM_THREADS` 未設定なら 1 に強制)は変更なし — 3.2/3.5 節参照。
- `src/diffusion.cpp`: `run_ted` の `OmpThreadGuard(1)` は変更なし
  (コメントに W-4 の検討結果を追記のみ)。

## 5. 検証

- 決定性テスト: `test_topology_parallel`, `test_species_parallel`,
  `test_rcm`, `test_mc` を実行し、既定(CPROCESS_THREADS 未設定、1
  スレッド、変更なし)で PASS を確認。`test_species_parallel` は
  `CPROCESS_THREADS=2/4/8` では FAIL することを実測で確認済み(3.2 節)
  — これは想定内(オプトイン時の既知の制約として 3.5 節に記載)であり、
  既定(未設定)経路が PASS することが本タスクの合格基準。
- フルスイート(53 本)を 2 チャンクに分けて実行し PASS を確認
  (既定 CPROCESS_THREADS 未設定、つまり実質コード変更前と同じ実行内容)。
- 性能計測: 既定値を変更しない結論になったため、「既定設定での wall time
  短縮」という DoD 原文の数値目標は本タスクでは達成しない
  (3.5 節に理由と代替案を記載)。`CPROCESS_THREADS=N` を明示指定した場合の
  参考計測は 3.5 節に記載。

## 3.5 節: 実測データと DoD からの逸脱の記録

CLAUDE.md 共通規約 4「仕様の数値基準が実測と食い違う場合は、計測プログラム
による根拠と共にコード内へ逸脱を文書化」に基づき記録する。

- 実行環境: `nproc` = 4(コンテナ内、実際の物理コア数/仮想化特性は不明)。
  他 3 エージェント(W-1/C-1/C-3)が同一チェックアウトで並行してビルド/
  テストを実行しており、wall time 計測はノイズが大きい。
- `test_species_parallel` 単体実行(`build/test_species_parallel`):
  - `CPROCESS_THREADS=1`(既定と同じ): `maxrel=0`, PASS。
  - `CPROCESS_THREADS=2`: `maxrel=1.05e-12`, FAIL(閾値 1e-12)。
  - `CPROCESS_THREADS=4`: `maxrel=1.14e-12`, FAIL。
  - 既定(何も設定せず、環境の `omp_get_max_threads()` が示す値、
    このコンテナでは 4): 変更前のコード(`min(hw,8)` 既定案)で
    `maxrel=1.68e-12`, FAIL。
- 元の DoD(「4 コア環境で ted/oed/ox2d 系テストの実測 wall time が既定
  設定で短縮」)は、既定値を変更しない結論としたため**未達成**。
  この逸脱の根拠は上記の実測 FAIL であり、CLAUDE.md 規約 4 に従い
  ここに明記する。既定を上げて速度を得るより、決定性保証を壊さないことを
  優先した。将来 W-4 の速度目標を達成するには、(a)
  `test_species_parallel` のような「経路間 bit 近接一致」を要求するテスト
  自体をスレッド数に依存しない形(例: 各経路を明示的に 1 スレッドで実行
  してから比較する、または許容誤差をスレッド数依存の緩い値にする)へ
  改修するか、(b) 高スレッド数と決定性保証を両立させる並列 reduction
  順序の固定化(例: reduction を毎回同一の木構造で行う実装)を先に
  導入する必要がある。いずれも本タスクの範囲外として次タスクへ委ねる。

## 6. 運用時の確認方法(検査セクション)

エンジニアが実効スレッド数を確認/調整する方法:
- 環境変数 `CPROCESS_THREADS=N` を設定して起動すればその値が使われる
  (`OMP_NUM_THREADS` より優先)。`CPROCESS_THREADS=1` で旧来の安全策に
  完全に戻せる。
- 何も設定しない場合の実効値は `min(std::thread::hardware_concurrency(), 8)`
  であり、`omp_get_max_threads()` を返す任意の C++ 呼び出し
  (例: `python3 -c` から `_cprocess` 経由で薄いラッパーを呼ぶ、または
  既存の `ted`/`diffuse` ログに `omp_get_max_threads()` を出力させる)
  で確認できる。本タスクでは追加のログ出力は行っていない
  (`ensure_sane_thread_count()` は低頻度のホットパス補助関数であり、
  毎呼び出しログは意図的に避けた)。将来必要であれば `proc::` 層で
  1 回だけ INFO ログを出す仕組みを追加できる。
- `run_ted` 経路は本タスクの変更後も常に 1 スレッド固定(3.4 節参照)。
  TED のみ並列化したい場合は、CLAUDE.md の構造模型不変条件に従い
  `run_ted` を直接いじるのではなく、将来のタスクとして
  ガード範囲の再検討(実測データが取れる環境で)を行うこと。
